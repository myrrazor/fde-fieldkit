Plugins

Fieldkit is one small core plus eight shipped plugins. Add only the tools you need. This page is the manager reference: list, add, remove, and update, where installs come from, what a missing tool looks like, and how to write a plugin of your own.

Not on PyPI yet The fieldkit packages are not on PyPI yet. Today plugin add resolves tools from your repo checkout, from the git subdirectory once the repository is public, or from a wheelhouse directory you point it at. PyPI installs arrive with the public release.

One core, tools you add

The fieldkit package carries what every tool shares: the CLI shell, table IO, PII scanning, report rendering, and the local web hub. Each tool is its own package named fieldkit-<tool> with its own dependencies, so a machine that only needs scrub never downloads the rest. Adding a tool is one command, and removing it is just as clean:

The whole lifecycle 
fieldkit plugin list
fieldkit plugin add xray scrub
fieldkit plugin update
fieldkit plugin remove scrub

plugin add

Takes one or more tool names and installs their packages into the same environment the core runs from. Extras ride along per tool. A wheelhouse directory selects local Fieldkit wheels; other dependencies may still be retrieved from a package index:

Add tools, extras, or wheels 
fieldkit plugin add xray scrub
fieldkit plugin add tell --extra ml
fieldkit plugin add xray --wheelhouse ./dist
Flag Default What it does
NAMES... required Tool names, e.g. xray scrub. Unknown names fail loudly with the known list.
--source auto Force local or git. Auto prefers a local checkout, then the git subdirectory. pypi is refused until packages are published (the PyPI name fieldkit is an unrelated project).
--extra NAME none Optional extras for a tool, e.g. --extra ml for tell. Repeatable.
--wheelhouse DIR off Resolve Fieldkit packages from local wheels. Other dependencies may still require network access.

plugin remove and plugin update

plugin remove uninstalls the named tool packages; the core and anything a tool wrote, like your debrief log, stay put. plugin update reinstalls at the newest version, defaults to everything installed when you name nothing, and accepts the same --source and --wheelhouse options as add.

Remove and update 
fieldkit plugin remove scrub
fieldkit plugin update
fieldkit plugin update xray --wheelhouse ./dist

When a tool is missing

Running a registry tool you have not added never dumps a Python traceback. The CLI tells you what it is and how to get it, then exits with status 2 so scripts fail loudly instead of half-running:

Real transcript 
$ fieldkit xray
'xray' is a Fieldkit tool that isn't installed yet.
  fieldkit plugin add xray

Where plugins install from

plugin add builds one pip requirement per tool and installs it into the running environment, using uv when it is available. The source is picked in this order unless you force one:

Source When it applies What happens
Repo checkout You are running fieldkit from a fde-fieldkit checkout. The default today. The tool installs straight from plugins/fieldkit-<tool> on disk.
Git subdirectory No checkout on disk, once the repository is public. pip pulls the package from the GitHub repo's plugins/ subdirectory.
Wheelhouse --wheelhouse DIR. Local wheels and pre-release testing. Fieldkit packages resolve from local wheels; other dependencies may still contact a package index. This option does not enforce offline installation.
PyPI Not available yet. Do not use --source pypi. Fieldkit packages are not published. The PyPI project named fieldkit is unrelated. Prefer uv sync from a checkout, git subdirectory installs, or a local --wheelhouse.

The hub dims what you have not added

fieldkit serve starts the local web hub on loopback. It prefers port 8765 and picks a free port if that one is taken; the command prints the URL. Tools you have installed are live cards with drag-and-drop. Registry tools you have not added stay on the board, dimmed, with their exact fieldkit plugin add command printed on the card, so whoever is driving the browser knows what to ask for. Nothing about the page needs a rebuild; the hub reads the environment on startup.

Working from the repo

A dev checkout is a uv workspace, so one command installs the core and all eight tools editable, which is why the worked examples across these docs use the uv run prefix:

Dev checkout 
uv sync
uv run fieldkit plugin list

Write your own

A new tool is a new package under plugins/fieldkit-<name> that exposes a typer app in the fieldkit.plugins entry-point group, plus one registry line in the core. Expose a module in the fieldkit.web group and the hub mounts its web page too. Plugins import shared table IO and PII scanning from the core and never import each other. Any installed package with the entry point shows up in fieldkit plugin list, and packages from outside the registry are labeled third-party. The AGENTS.md file in the repository spells out the full contract.
